How GolfNow actually works

It's not really a golf company. It's a two-sided marketplace whose real product is software the courses can't afford to say no to.

The one thing to understand the model

GolfNow gives a golf course its tee-sheet software, point-of-sale, CRM, website booking, and app placement — often for little or no cash. In return, the course hands GolfNow a block of tee times every day. GolfNow resells those as discounted "Hot Deals." That's the famous barter model: tech-for-inventory, not cash-for-commission.

Why that's genius (and controversial)

  • Supply lock-in: once a course runs its whole operation on GolfNow's tee sheet, leaving means ripping out the system that runs the pro shop. That's a moat.
  • Aggregation: 9,000+ courses, 3M+ golfers. One app, every course — the golfer never needs another. Classic network effect: more courses → more golfers → more courses.
  • The backlash: discounting tee times "80% off or free" trains golfers to never pay rack rate, and courses feel they've abdicated pricing. Know this — it's the opening for a competitor.

The technical spine (this is the part that upgrades Fairway)

1
The tee sheet is the source of truthA cloud database of every slot: time, price, players allowed, cart/rider fees, restrictions. Lives on GolfNow's servers, synced in real time.
2
An availability API reads itThe app calls a real-time API → gets back open slots + live pricing + player limits. Refreshes constantly so two people can't grab the same 8:10am.
3
A reservation API writes to itBooking = a two-way call that validates restrictions, applies fees, takes payment, decrements the slot, and fires a confirmation. This is the hard part.
4
Distribution via open APIsThe same inventory is published to third-party distributors (Supreme Golf, Golfback, Barstool Golf…) through open APIs — one tee sheet, many storefronts. That's "distribution."
The honest gap in your Fairway demo. Yours already beats GolfNow on discovery and UI. What it can't fake is steps 1–3: a live tee sheet (needs a distributor/course API), real payment (needs Stripe + a business), and licensed photos. Those are business deals, not code.
Your realistic path to "real": don't rebuild GolfNow's supply. (1) Aggregate course-owned booking links (you already open their site) → zero integrations, launch tomorrow. (2) Add one distributor API (Supreme Golf / a tee-time gateway) for real inventory in one region. (3) Add Stripe only when you're taking a cut. The wedge that beats them: be the finder golfers actually trust — no dark-pattern discounting, real course info, hidden gems.

APIs — the whole idea in 5 minutes

An API (Application Programming Interface) is a menu one program offers another: "here are the things you can ask me to do, and the exact format to ask in."

The restaurant mental model

You (the client) don't walk into the kitchen. You read the menu (the API), tell the waiter (the request) what you want, and the kitchen (the server) sends back a plate (the response). You never see how the kitchen works — that's the point. APIs hide complexity behind a contract.

REST — the style 90% of web APIs use

You act on resources (a course, a booking, a user) at URLs, using HTTP verbs:

VerbMeansExample
GETread (never changes anything)GET /courses?near=27526
POSTcreatePOST /bookings
PUT / PATCHupdatePATCH /bookings/88
DELETEremoveDELETE /bookings/88

What comes back: JSON + a status code

// the server's reply to GET /courses/12
{
  "id": 12,
  "name": "Cedar Ridge Links",
  "holes": 18,
  "teeTimes": [ { "time": "08:10", "price": 42 } ]
}
  • JSON is just labeled data — key: value. Every language reads it. It's the lingua franca of APIs.
  • Status codes tell you what happened: 200 OK · 201 created · 400 you sent junk · 401 not logged in · 403 not allowed · 404 not found · 429 slow down · 500 their bug.

Auth — proving who you are

MethodWhat it isUsed for
API keya long secret string in a headersimple service-to-service (weather, maps)
OAuth 2.0"log in with Google" — you never see the passwordacting on a user's behalf
JWT / tokena signed pass that proves you logged in, expireskeeping a session after login
Rule that will save you: a secret (API key, token) never goes in front-end code or a git commit. It lives in an environment variable on the server. Leaked keys get abused within minutes.

Two more you'll hear

  • Webhook — the reverse of an API call. Instead of you asking "any news?", they call you when something happens (Stripe pings your server when a payment clears). "Don't call us, we'll call you."
  • Rate limit — "max 100 calls/minute." Exceed it → 429. You handle it by backing off and retrying.

Networking — the layer you're being hired for

Everything is just packets finding their way from one machine to another. Master the path a request takes and you understand 80% of the job.

The models: OSI (7 layers) & TCP/IP (4) memorize

Interviews love the OSI model. Mnemonic top-down: "All People Seem To Need Data Processing."

#LayerDoesYou'll say
7Applicationthe app talksHTTP, DNS
6Presentationformat/encryptTLS/SSL
5Sessionkeep the convo—
4Transportreliable delivery + portsTCP, UDP
3Networkrouting between networksIP, routers
2Data Linksame-wire deliveryMAC, switches
1Physicalthe actual signalcable, wifi

Follow one request: you type a URL, hit enter

1
DNSYour machine asks a DNS server "what's the IP for golfnow.com?" → gets 104.18.x.x. DNS is the internet's phone book (names → numbers).
2
TCP handshakeYour machine and the server do a 3-step "SYN → SYN-ACK → ACK" to open a reliable TCP connection on port 443.
3
TLSThey swap certificates and set up encryption — the https padlock. Now nobody in the middle can read it.
4
The request routesYour packet hops router → router across networks, each reading the destination IP and forwarding it closer. That's routing.
5
Response comes backThe server sends HTML/JSON back down the same path. Milliseconds.

The vocabulary that gets you hired

TermIn one line
IP addressa machine's number. IPv4 = 192.168.1.10; IPv6 = the longer new one (we ran out of IPv4).
Subnet / CIDRslicing an IP range into networks. /24 = 256 addresses. Subnetting is the #1 thing to drill.
Porta numbered door on a machine. 80=HTTP, 443=HTTPS, 22=SSH, 53=DNS.
TCP vs UDPTCP = reliable, ordered (web, email). UDP = fast, lossy (video, games, DNS).
Router vs switchswitch connects devices inside one network (L2/MAC); router connects between networks (L3/IP).
VLANone physical switch split into isolated virtual networks.
NATmany private devices sharing one public IP (your home router does this).
Firewallrules for which traffic is allowed in/out (by port, IP, protocol).
Load balancerspreads traffic across many servers so none tips over.
VPNan encrypted tunnel making a remote machine act like it's on the local network.
OSPF / BGPhow routers decide paths. OSPF = inside one org; BGP = between orgs (runs the whole internet).
Drill these two to stand out fast: subnetting (given 10.0.0.0/26, how many hosts? which range?) and "walk me through what happens when I load a website" — the flow above. Nail both cold and you interview above your experience level.

Cloud — renting someone else's computers, well

"The cloud" = data centers you rent by the minute via an API, instead of buying servers. The skill is knowing which service to reach for.

The three rental levels

  • IaaS (Infrastructure) — they give you a bare virtual machine, you install everything. Most control. e.g. AWS EC2.
  • PaaS (Platform) — you hand them code, they run it. No servers to manage. e.g. a managed app host.
  • SaaS (Software) — finished software you just use. e.g. Gmail, GolfNow's tee sheet.

Analogy: IaaS = lease an empty kitchen · PaaS = a kitchen with staff, you bring recipes · SaaS = order the meal.

The core primitives (every cloud has these — learn the concept once)

ConceptAWSAzureWhat it is
Virtual machineEC2Virtual Machinea rented computer
Object storageS3Blob Storageinfinite bucket for files
Private networkVPCVNetyour own isolated network in the cloud
Identity/permissionsIAMEntra IDwho can do what — the security core
Serverless functionLambdaFunctionsrun code with no server, pay per call
Managed databaseRDSAzure SQLa database they keep alive

Words that matter for the networking/cloud role

  • Region & Availability Zone — a region is a geographic area; AZs are separate data centers in it. You spread across AZs so one fire doesn't kill you.
  • VPC networking = the same subnets, route tables, firewalls (called security groups) and gateways from Section 3, but virtual. Your networking knowledge maps directly onto cloud. That's your bridge.
  • IaC (Infrastructure as Code) — define your whole network/servers in a text file (Terraform) and deploy it repeatably. This is the modern job.
  • Container (Docker) — package an app + everything it needs into one portable box. Kubernetes runs thousands of them.
  • CI/CD — automated pipeline: push code → it tests → it deploys. No manual steps.
The 6-month path everyone recommends, in order: networking fundamentals → one cloud (pick AWS or Azure, don't split) → Linux + a scripting language → Terraform (IaC) → Docker/containers → CI/CD. Depth in one beats shallow in three.

AI & LLMs — what's under the hood

The AI you care about is the LLM (Large Language Model) — the thing running this guide's author. Here's how it actually works, minus the hype.

What an LLM really does

It's a giant math function trained on a huge slice of text to do one thing: predict the next chunk of text. Everything — answering, coding, reasoning — is that prediction, done extremely well. It is not a database and it doesn't "look things up" unless you give it a tool to.

The five terms that unlock every AI conversation

TermMeaning
Tokena piece of a word (~4 chars). Models read/charge/limit by tokens, not words.
Context windowhow much it can "hold in mind" at once (its short-term memory). Overflow = it forgets the start.
Training vs inferencetraining = the months of learning (done once, costs millions). Inference = you asking it something (cheap, instant).
Prompteverything you send in. Prompt quality is the single biggest lever on output quality.
Hallucinationconfident wrong answers. It predicts plausible text, not truth — so you verify, or give it tools/data.

The patterns that turn a chatbot into a product

  • RAG (Retrieval-Augmented Generation) — before answering, fetch relevant documents and paste them into the prompt. How you make an LLM answer from your data (a company's docs) without retraining.
  • Embeddings — turning text into a list of numbers so a computer can find "similar meaning." The search engine behind RAG.
  • Tools / function calling — you hand the model functions (search, send email, run code). It decides when to call them. This is the leap from "talks" to "does."
  • Agent — an LLM in a loop with tools and memory, working toward a goal across many steps. Your Bee is exactly this. So is the hourly loop running your repo.
  • Fine-tuning vs prompting — prompting/RAG solves 95% of cases and is cheap. Fine-tuning (retraining on your examples) is a last resort. Don't reach for it first.

The API shape (this is literally how you'd build with me)

# you POST a prompt, you get text back — same REST from Section 2
POST https://api.anthropic.com/v1/messages
{
  "model": "claude-...",
  "max_tokens": 1024,
  "messages": [ { "role":"user", "content":"..." } ]
}
Why this is your unfair advantage: most networking/cloud people fear AI. If you're the cloud/network hire who can also wire an LLM into a workflow — automate tickets, summarize logs, build an agent that watches infra — you're not late, you're early to the combination almost nobody has yet.

Programming me — loop engineering for around-the-clock work

You want to point me at your startups and work and have me grind while you sleep. Here's the anatomy of a prompt/loop that actually does that safely — the exact pattern already running your repo.

An autonomous loop needs four things (yours already has them)

  • A queue — an ordered list of work (your BACKLOG.md). The loop always takes the top. You steer by reordering it.
  • A contract — the rules every cycle follows (your LOOP.md + AGENTS.md): build → verify with real evidence → small reversible commit → log → repeat.
  • Guardrails — hard stops: never fake "done," never invent scope, never do anything irreversible/paid without a human. This is what makes unattended safe.
  • A trigger — what fires it: an hourly schedule, or a /loop you start in a session.

The anatomy of a good "do my work" prompt

# a self-contained autonomous prompt has these parts:
ROLE      you are X working on repo Y at path Z
SOURCE    read these files first (backlog, rules, state)
TASK      take the top item; do ONE fully
VERIFY    prove it works before claiming done (run it)
RECORD    commit small + log what/why/how-to-undo
GUARDRAIL stop for a human on anything irreversible
STOP      one item per run; say what's next

The rules that keep an autonomous agent from wrecking things

  • Small, reversible steps. One commit per unit, each with an undo. A bad cycle is a one-line rollback, not a disaster.
  • Evidence beats confidence. The agent must run the thing and read the output — "should work" is banned. This one rule prevents most silent failures.
  • It can add to the plan, not act on it. New ideas go into the backlog for you to approve — the loop can't expand its own mandate.
  • Humans gate the irreversible. Deploys, payments, deletions, settings — the agent prepares them and stops. You pull the trigger.
How to actually run your empire this way: one repo per venture, each with its own BACKLOG.md + LOOP.md. Point an hourly loop at each. You spend your time doing the one human job — reordering the backlogs — and wake up to committed, verified progress. That's the whole game. You've already built the template once; every future venture is a copy-paste of the pattern.
